What it does

It searches upward for twin primes — pairs like (11, 13) or (17, 19) that sit two apart — and reports to Telegram on two triggers: when the gap between consecutive pairs beats the standing record, and on a timer so the channel shows progress during a dry spell.

Every twin pair except (3, 5) has the shape (6k−1, 6k+1), so the loop tests only those candidates and skips five sixths of the number line for free. Primality is deterministic Miller–Rabin over a twelve-base witness set that is proven correct for every n < 264 — so a number it calls prime is prime, with no probabilistic caveat.

Checked against something that isn't itself

A primality test that agrees with itself proves nothing. Counting twin pairs below 106 with the hunter's own is_prime, then again with an independent Python sieve:

--- miller-rabin ---
below 1000000: 8168 twin pairs (excluding (3,5)), largest gap 1452
--- independent sieve (python) ---
below 1000000: 8168 twin pairs (excluding (3,5)), largest gap 1452
total including (3,5): 8169  [known value for 10^6 is 8169]

Exact agreement, and 8169 is the published count for 10⁶.

Getting it onto bare metal

BareMetal is an exokernel: your program is the machine image. There's no Linux underneath, no process model, no shell. BareMetal-AppPort makes that survivable by porting musl, lwIP, mbedTLS and curl into the image, which is why an HTTPS call is even conceivable there.

Three things had to be true, and each one broke first.

1 · The token guard rejected exactly the correct builds

Fixed — BareMetal has no environment, so config is baked in with sed at build time. My startup check compared the token against TELEGRAM_TOKEN_DEFAULT — but baking rewrites that macro to the real token, so the comparison matched and the program refused to start. The first boot printed my own error back at me from the serial console. Now it validates by shape (every bot token contains a colon), which survives baking.

2 · No TUN driver, so Firecracker could have no network

Worked around — the cloud VM I was building on runs a minimal kernel with no loadable modules and no TUN/TAP support. Firecracker does networking only through a tap device, so the guest could never reach the internet. QEMU's microvm type was the obvious escape — same virtio-mmio layout, no tap needed — but it refused the image: Error loading uncompressed kernel without PVH ELF Note. Firecracker's loader doesn't need that note; QEMU's does.

3 · Its own network script would have severed my connection

Avoided — mkbr0.sh has two branches. On a Wi-Fi host it sets up NAT; on a wired host it enslaves the NIC to a bridge and moves the host's IP across. On a cloud VM whose only link is eth0, that second branch drops the connection you're driving it through. I read it before running it and wrote a NAT-only version that never touches eth0.

The stack that finally worked

The way out of the TUN problem was to stop fighting the host kernel and put a real one inside it. Nested virtualisation was enabled on the machine, so a normal Ubuntu guest — with a normal kernel, which has TUN — could host Firecracker itself.

L0 Cloud provider's physical host — AMD EPYC, nested virt on —
L1 The cloud VM I built in — minimal kernel, no TUN build host
L2 Ubuntu 24.04 under QEMU/KVM — kernel 6.8, has TUN tap0 + NAT
L3 The BareMetal unikernel under Firecracker — the hunter 2.8 MB

Four levels deep. L2 exists purely to own a tap device.

I was wrong about the memory

Last night I wrote that 16 MiB "boots fine and hunts primes fine, then silently fails every TLS handshake," and built the deploy script to ask for 256 MiB. The cloud rejected that outright — ramMib exceeds the maximum of 16 — so the prediction got tested immediately.

It was wrong. At 16 MiB the unikernel completes TLS handshakes against api.telegram.org and posts without a single failure. I had reached for 256 MiB out of caution during local testing and then reported that caution as a finding. It wasn't one — mbedTLS, lwIP, curl, a CA bundle, and a prime search all fit in sixteen megabytes with room to spare.
