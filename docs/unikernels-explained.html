Unikernels, exokernels, and a weekend of measuring one

The Program Is the Machine

We built an LLM agent that runs with no operating system beneath it — no kernel, no init, no shell — in 16 MiB of RAM. This is what that means, how it works, and what it measured when we pushed on it.

Start with what a kernel is for

An operating system kernel does two jobs that are worth separating in your head, because the whole story turns on the distinction.

The first is protection: many programs share one machine, so something has to stop them reading each other's memory or writing each other's files. The second is abstraction: rather than handing you a network card, the kernel gives you a socket; rather than sectors, a file; rather than a CPU, a scheduled thread.

Abstraction is genuinely useful and almost never free. The kernel's idea of a file, a socket, or a scheduling policy is a compromise chosen for everyone, and a program with unusual needs pays for the compromise while being unable to change it. Database authors have complained about this for decades: the kernel's page cache and its notion of when a write is durable are frequently wrong for a database, and there is no way to opt out of them, only to fight them.

There is also a cost you can measure. Every request from your program to the kernel crosses a protection boundary, with the register saving and cache disruption that implies. Containers do not remove that boundary; they add namespacing and cgroups above the same kernel, so a containerised process makes exactly the same system calls with more bookkeeping around them.

The exokernel idea

In 1995 a group at MIT — Dawson Engler, Frans Kaashoek and James O'Toole — published a design that took the two jobs apart. Their argument was that a kernel should do the first job and get out of the way of the second: securely multiplex the hardware, and let applications implement their own abstractions.

An exokernel exposes hardware resources — disk blocks, memory pages, network packets, slices of CPU time — with protection and nothing else. The abstractions move into a library operating system that is linked into the application. If your program wants a filesystem, it links one; if it needs something unusual, it links a different one, or none at all. The kernel stops being an authority on what a file is.

The idea was influential and, for a long time, mostly academic. What revived it was virtualisation: once a hypervisor is the thing multiplexing the hardware among tenants, the protection job is already being done underneath, and the case for a general-purpose kernel inside each guest gets much weaker.

Which gives you unikernels

A unikernel is the logical end of that line. Take the application, take only the parts of a library OS it actually calls, compile them together into a single address space, and the result is a bootable machine image. No processes, because there is only one program. No system calls in the usual sense, because there is no boundary to cross — a "syscall" is a function call. No shell, no package manager, no init system, because nothing else is ever going to run there.

The term was popularised by the MirageOS work around 2013, and there are now several serious implementations — MirageOS, IncludeOS, Unikraft, OSv, Nanos among them. They differ in language and philosophy but share the shape: one program, compiled with its operating system, booting as the machine.

What actually gets removed

The consequences follow directly from the picture. The attack surface is what you linked and nothing else: there is no shell to get, no second process to pivot into, no package manager to exploit. The image is small because unreferenced library code is never linked. Boot is fast because there is no userland to bring up. And the whole thing is a single artifact, so "what is running in production" has one answer.

The costs are equally direct. One program means no sidecars and no local tooling. No shell means no logging in to look around when something is wrong — you get the serial console and whatever you thought to print. Configuration usually has to be compiled in. And when something in the library OS is wrong, you cannot apt-get the fix; you rebuild.

BareMetal, specifically

The system we used is BareMetal by Return Infinity: an exokernel written from scratch in x86-64 assembly, with an accompanying project, BareMetal-AppPort, that ports the library OS pieces an ordinary C program expects — musl for libc, lwIP for TCP/IP, mbedTLS for TLS, libcurl for HTTP, plus SQLite, libsodium, lwext4 and even CPython.

That combination is what makes the exercise interesting. You write ordinary C, against ordinary APIs, and what comes out is a bootable machine image of a few megabytes that runs under Firecracker with no Linux anywhere in the picture.

What we built on it

Four programs, each pushing on a different property of the platform.

1 · A prime search that phones home

The first question was whether a unikernel could hold a TLS conversation with a public API at all. A twin-prime search that posts its records to Telegram answered it: 24 HTTPS POSTs, 24 acknowledged, zero failures, inside a 16 MiB instance — mbedTLS, lwIP, curl and a full Mozilla CA bundle all resident alongside the running search.

We had budgeted 256 MiB for the TLS handshake. The platform's per-instance ceiling turned out to be 16 MiB, which rejected our deployment, and it then worked at 16 MiB anyway. That prediction was published before it was tested, and it was wrong.

2 · A swarm with no coordinator

Three instances hunting Cunningham chains — primes where p, 2p+1, 4p+3 and so on are all prime. Coordination used no queue, no database and no leader: worker i of N takes the candidates where k ≡ i (mod N). Coverage is complete and disjoint by arithmetic, and a worker dying costs exactly its own share.

It found 56 chains, six of length nine, each re-verified afterwards with an independent implementation. The smallest:

198,479,579 → 396,959,159 → 793,918,319 → 1,587,836,639 → 3,175,673,279
→ 6,351,346,559 → 12,702,693,119 → 25,405,386,239 → 50,810,772,479

It also failed instructively. The first partition split the odd numbers by index, which quietly pinned each worker to a fixed residue class mod 6 — and two of the three classes cannot produce a chain at all. One worker could never extend past length 1, another never saw a prime, and both looked perfectly healthy: running, networked, error-free, heartbeating. Effective parallelism was 1 for several hours before the arithmetic gave it away.

3 · An agent that supervises the swarm

The workers are dumb C loops, which is correct — testing primes needs no model. What needs one is "is worker 1 broken, and if so, what broke?", because the branch tree is not enumerable: it crashed, it was reclaimed, DNS failed, quota hit, or it is perfectly healthy and its slice of the number line simply had nothing to announce — in which case silence is correct and intervening is the bug.

That last case is exactly what went wrong first, and the fix generalises well beyond this project. It is in the last section.

4 · An agent you can text

The one that ties it together: an LLM agent with tool calling, running as a unikernel, that anyone can hold a conversation with. Its tools mostly report on the machine it inhabits, so its answers are measurements rather than claims.

It allocates nothing on the heap. cJSON is pointed at a static bump arena through cJSON_InitHooks, the buffers are fixed arrays, and partway down the file the allocator ceases to exist:

#define malloc   DO_NOT_malloc
#define realloc  DO_NOT_realloc
#define free     DO_NOT_free

Any code added below that line fails to compile if it reaches for the heap. A typical answer uses 8–54 KB of a 384 KB arena, which is reset after every exchange — so memory is bounded by one question rather than by uptime.

Memory on a machine with no disk

Cloud instances turned out to have no writable filesystem at all: open(O_CREAT) fails with ENOENT. The same binary on a local run with a real 512 MB disk writes happily and the value survives a restart, so this is the platform, not the program.

So its memory lives a network round-trip away — Redis behind an HTTP interface, reached over the same TLS stack as everything else. At boot it proves the path and, incidentally, counts its own restarts:

[+] memory reachable: this is boot #3, remembered across restarts

The key is built in C from the incoming chat id, never chosen by the model — so it cannot read another person's notes however it is asked to.

One finding that matters more than the rest

The runtime does not compute deterministically for our workload. Three passes over an identical fixed range, inside a single boot, returned three different prime counts — always undercounts. It reproduces on real cloud hardware as well as on a nested-virtualisation host, it is unaffected by memory size, and Linux is exactly deterministic at both -O0 and -O2.

A forty-line reproducer isolates it to 64-bit modular arithmetic with no primality logic, no allocation and no libc call in the loop: 20,000,000 evaluations of one fixed modular exponentiation give 0 mismatches on Linux and 32 in the unikernel. We could not determine the cause; interrupt-time register preservation in the guest is the first thing we would audit, because it predicts the signature — a low, rate-dependent error frequency in a long-running compute loop.

The practical consequence for a search workload is that it silently misses results. It does not invent them — everything the swarm reported was independently verified — so finds stay trustworthy while coverage cannot be called exhaustive.

When this shape makes sense

The case for unikernels is strongest where the workload is a single long-lived network service with a narrow job: an edge function, a protocol gateway, a metering or signing service, a bot. You get a tiny attack surface, an image measured in megabytes, a fast start, and one artifact that is unambiguously what is running.

The case is weakest where you need the things a kernel is good at. Multiple cooperating processes, a shell for the 3 a.m. investigation, dynamic configuration, mature observability, a filesystem you can rely on, or a team who can debug what they already know. Our own experience is a fair sample: the platform did everything advertised, and every hour we lost went to something adjacent — a network script that would have disconnected the host, a build flag that made a benchmark meaningless, an absent filesystem, an arithmetic bug we could reproduce but not explain.

Neither list is a verdict. They are the shape of the trade, and it is a real trade rather than a free lunch.

The lesson that generalises

Three of our four programs are agents, and the same mistake happened in all three. It is worth naming because it is not about unikernels at all.

The supervisor's job was to notice broken workers and restart them. Its system prompt said, in plain words, that a worker with no recent findings is not necessarily unhealthy. On its first run against a completely healthy swarm, it restarted a worker anyway — reasoning that it had "only reported best 1", which indicated no finds. The restart left that instance stopped, so the intervention degraded the system it was meant to protect.

The fix was not a better sentence. It was moving the decision out of the model's reach: health computed in C from status, network and error lines, with find counts excluded by construction; a restart tool that refuses a healthy target and cannot be argued past; one corrective action per run, counted in a variable. After that, the healthy-swarm run took zero actions and the fault-injection run detected, restarted, re-verified and reported.

The same pattern recurred everywhere. The research agent cited URLs it had never fetched, so citations are now checked against what the run actually retrieved. The chat agent announced "I need to search for that" and stopped, leaving the person with a sentence and no answer.

Guardrails in code, judgement in the prompt

If a rule must hold, encode it where the model cannot reach: a validated enum, a refused call, a counter, an allowlist. Prompts are requests. A limit that lives in a prompt is a limit you are hoping for.

The corollary matters too, and is easy to over-apply: things that are genuinely judgement — which query to try next, whether the evidence settles the question, when to open a file rather than search again — belong in the prompt, and trying to encode them in C produces a brittle mess. Two of our fixes went one way and two went the other, and telling them apart is most of the skill.

Reproducing any of it

github.com/tabibazar/unikernel-c — the prime hunter, the Cunningham swarm, the supervising agent, a stateless research agent, the benchmark harnesses and the nondeterminism reproducer, plus a technical report with the full measurements.

github.com/tabibazar/baremetal-agent — the agent you can text, with build instructions for Linux, macOS, a local Firecracker run, and BareMetal Cloud; the self-hosted Redis-over-HTTP memory service; and the disk test that established there is no local filesystem.

Everything builds from the same source on Linux, macOS and BareMetal, which is what makes it practical to develop: iterate as an ordinary binary in seconds, then rebuild as a machine image in about one more.

Written after two days of building on BareMetal and BareMetal-AppPort by Return Infinity, whose responsiveness to a stream of bug reports is the reason the harder measurements exist at all. Every figure here was measured rather than recalled; where a cause is unknown, it is labelled unknown.
