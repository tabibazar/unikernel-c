Ant colony optimization · fixed compute budget

How far you can split a search before it stops working

Give a hundred workers a two-hundredth of the compute each and they match one long run exactly. Give a thousand workers a thousandth and the whole thing falls apart. The boundary is sharper than expected — and it isn't where you'd guess.

The question

If you have a fixed amount of compute, is it better spent as one long search or many short independent ones? It sounds academic. It decides whether a swarm of tiny, cheap, short-lived machines is a sensible way to compute anything.

Every arm below spends exactly 200,000 ant constructions on the same 442-city routing problem. The only difference is how that budget is chopped up. Results are combined by taking the best tour any worker found — which needs no communication at all, and is the only reason a swarm of isolated machines could work in the first place.

The cliff isn't about worker count

Nothing goes wrong because there are too many workers. It goes wrong because each one becomes too short to finish what it starts.

This algorithm spends its first iterations building up structure from a crude starting route. A worker that dies before that structure forms contributes almost nothing — barely better than where it began. Ten thousand of those are worth less than one run that actually got somewhere.

Give every worker a couple of seconds of real work. Then have as many as you like.

That is a floor on task size, not on parallelism, and it is the useful form of the answer. The knee sits between 500 and 1,000 iterations — here, between 0.9 and 1.8 seconds.

Why this matters for tiny machines

A worker that must live for about two seconds anyway can afford a startup cost of a few tens of milliseconds. Measured against that floor:

StartupCostOverhead at a 1.8s task
Unikernel, no OS31 ms1.7%
AWS Lambda (measured)45 ms2.5%
Linux guest under Firecracker950 ms53%

So the ephemeral-swarm idea survives, with an actual number attached instead of a hope — and the number says the interesting comparison is not between a unikernel and a serverless function, but between either of those and booting a general-purpose operating system per task.

What it doesn't show

The prediction going in was wrong. It was written down first: monotonic degradation, one long run winning outright. The truth is a plateau and then a cliff, and the plateau reaches far further than expected. Recorded because a prediction only counts if you keep it after it fails.

It is one workload. This algorithm accumulates memory across iterations, which arguably makes it the least splittable search one could have picked. That the plateau still reaches 200 workers is encouraging, but it is evidence about this problem, not about search in general.

The seconds are instance-specific. The 1.8-second floor is 1,000 iterations on this particular map. The number that transfers is the iteration count, not the clock.
