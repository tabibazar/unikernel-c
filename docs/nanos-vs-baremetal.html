One host · five runs of everything · 29 August 2026

Nanos vs BareMetal

Only two other platforms in the field run unikernels. This is a head-to-head against one of them, on a single machine, with the same C source on both sides — and a control that settles a question we had been carrying for weeks.

Boot to first instruction

8×

BareMetal reaches its application in 31 ms against Nanos' 240 ms. Thirty-one times faster than Linux under the same hypervisor.

Smallest memory it runs in

4 MiB

Nanos will not boot below 16 MiB. No competitor in the wider field sells a unit under 128 MB.

Compute, identical source

3.7×

BareMetal takes 51.7 s where Nanos takes 14.1 s. Not the compiler, not the hypervisor.

Wrong answers per run

~1360

Out of 20 million identical calculations. Nanos and Linux: zero, every run.

The setup, and its one honest caveat

Everything ran on one machine: an AMD EPYC host with 2 shared vCPU, 8 GB and hardware KVM. Comparing across two clouds measures the clouds, so there is only one. Five runs of every configuration; the numbers below are medians, because two shared vCPUs make a single timing a statement about scheduling luck.

Each guest runs under the virtual machine monitor its own platform ships with, because neither would boot under the other's. BareMetal's ELF carries no PVH note, so QEMU's microvm refuses it outright; it runs under Firecracker 1.16.1 — which is also what BareMetal Cloud runs. Nanos boots from a disk image with its own loader under QEMU 8.2.2 with KVM, which is what ops runs. Both get one vCPU, 512 MiB, and a serial console piped through a timestamper.

That is a real confound, and it is why the control below exists.

The optimisation question, settled first

BareMetal's build script passes no -O flag at all, so its application is compiled at -O0. Every Linux and Nanos binary was therefore built both ways. On this workload -O0 against -O2 is 14.01 s against 12.85 s — about 8%. Worth knowing before reading a 3.7× gap as a compiler flag.

Boot: BareMetal wins by an order of magnitude

NanoVMs publishes “~60 ms” for boot. That is defensible as raw kernel time — Nanos has its network up at about 0.19 s — but what a user waits for before their own code runs is nearer 0.24 s, four times the headline. Return Infinity publishes no boot figure at all, and would win this column decisively if it did.

And the memory floor, found by walking the same trivial program down until it stopped working: BareMetal runs in 4 MiB and fails at 3. Nanos runs in 16 MiB and fails at 12. For scale, the smallest unit any competitor in the wider field will sell you is 128 MB.

Compute: 3.7× slower, and it is not what you would guess

Three explanations are eliminated by the rows above. Not the compiler, because -O0 against -O2 is 8% and the gap is 370%. Not the hypervisor, because Linux under the same Firecracker lands within 1% of native. Not the host, because everything ran on it. Something in the BareMetal port is paying 3.7× for 64-bit modular arithmetic, and this experiment does not say what — it only narrows the field.

Determinism: the result that needed a control

The test computes one fixed modular exponentiation twenty million times. The inputs never change, so a correct machine returns the same answer twenty million times and the mismatch count is zero by construction. Anything else is the machine giving two different answers to the same question.

The rate here is 6.8 × 10⁻⁵, against 1.6 × 10⁻⁶ measured earlier on different hardware — roughly forty times more frequent on this host than where it was first caught.

It returns wrong answers, not just a warning counter

The second program counts primes over a fixed range. The work is deterministic, so every run must produce the same count. Five BareMetal runs:

primes=4267876
primes=4267777
primes=4267803
primes=4267888
primes=4267838

Five runs, five different answers. Linux and Nanos return 4268930 every single time.

The error is one-directional: BareMetal only ever undercounts, so the corruption is causing the primality test to reject genuine primes rather than accept composites — what you would expect if a value is being disturbed between a multiply and its comparison. About 1,100 primes in 4.27 million go missing, so roughly one result in four thousand is wrong, with nothing printed to say so.

Why this is the finding that matters

Return Infinity's stated vertical is quantitative research, compliance automation and trading infrastructure, sold on deterministic scheduling. A workload that silently returns a slightly different answer each run is a poor fit for that pitch, and this is a small enough reproducer — no allocation, no I/O, no threads, sixty lines — to be a starting point rather than a complaint.

What this does not measure

No TLS or HTTPS comparison. This host has no TUN driver, so a Firecracker guest on it has no network at all and BareMetal could not be given one. The 888 ms program-start-to-completed-HTTPS figure we have for BareMetal was measured on BareMetal Cloud, on different hardware, and is not comparable to anything here.

Nanos was run locally through ops, not on NanoVMs' hosted product, so nothing here evaluates their cloud — only their kernel. And two shared vCPUs make this a poor host for absolute throughput: the ratios are the result, the seconds are not.

Every number above is a median of five runs from serial logs timestamped on the host. The scripts, the raw logs and the full result table are in the repository, so the whole thing can be re-run on better hardware by anyone who doubts it — which, given what it claims, someone should.
