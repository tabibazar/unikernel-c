Technical report · 25–26 August 2026

Primes from Bare Metal

Two workloads — a prime search and an LLM agent loop — built as BareMetal unikernels and measured against the same code running as ordinary Linux processes. A complete TLS client fits in 16 MiB. A controlled experiment also found nondeterministic integer arithmetic in the unikernel, reproduced on two independent hosts, with a 40-line reproducer.

Abstract

We ported two C workloads to BareMetal via BareMetal-AppPort and deployed them to BareMetal Cloud: a twin-prime search reporting to a public HTTPS API, and a three-worker swarm hunting Cunningham chains, supervised by an LLM agent that diagnoses and repairs worker faults. We report four measurements. (1) A full TLS stack — mbedTLS, lwIP, curl and a Mozilla CA bundle — runs inside a 16 MiB instance alongside an active search, delivering 24 of 24 HTTPS requests with no failures. (2) Unikernel images are 1.3–2.8 MB. (3) On a single host, with optimisation level matched, the unikernel executed a fixed integer workload at 0.80 M candidates/s against 2.67 M/s for the same source as a Linux process, a 3.3× difference; the default BareMetal build additionally compiles at -O0. (4) The unikernel does not compute deterministically: three passes over an identical fixed range inside a single boot returned three different prime counts, all undercounts, on both a nested-virtualisation host (1.6×10−6 error rate) and BareMetal Cloud hardware (≈2×10−4). Linux, at both -O0 and -O2, is exactly deterministic. We isolate the effect to 64-bit modular arithmetic with a reproducer containing no primality logic, no allocation, and no libc call inside the loop. (5) Across two swarm deployments the workers searched to 1.29×1010 and found 56 Cunningham chains of the first kind, six of them of length nine, each re-verified independently after capture; sustained search throughput on cloud instances was ≈80,000 candidates/s per worker.

2 · A TLS client in 16 MiB

Method. The prime search was built as a unikernel with a Telegram bot token compiled in (BareMetal exposes no environment, so getenv returns nothing and compile-time defaults are used). It performs an HTTPS POST to api.telegram.org on each search milestone, with CURLOPT_SSL_VERIFYPEER and VERIFYHOST enabled and the CA bundle supplied explicitly — from /etc/ssl/cacert.pem when present on the disk image, otherwise from the bundle linked into the binary as cacert_pem. Success was counted in-program from the HTTP status, not inferred from absence of errors.

Result. 24 POSTs issued, 24 acknowledged, 0 failures, at MEMSIZE=16:

net: ready ip=172.19.0.148 mask=255.255.255.0 gw=172.19.0.1
[*] record gap 3480 at 255953429
[+] telegram ok (24 sent, 0 failed)

On BareMetal Cloud the same image obtains its address from Firecracker's boot arguments rather than DHCP — a different code path, exercised for the first time on deployment, which worked without change:

net: fc ip param fields: client-ip="172.16.0.10" gw-ip="172.16.0.1"
net: no DNS server provided by fc/DHCP, falling back to 8.8.8.8
net: ready ip=172.16.0.10 mask=255.255.0.0 gw=172.16.0.1
[+] telegram ok (1 sent, 0 failed)

Note on the 16 MiB figure. We initially assumed mbedTLS would need substantially more and configured local runs at 256 MiB. The platform rejected that at deployment (ramMib exceeds the maximum of 16), and the workload then ran correctly at 16 MiB. The prediction that 16 MiB would fail TLS was wrong, and is recorded here because it was published before being tested.

3 · Throughput, controlled

Method. A fixed-work benchmark — Miller–Rabin primality over a fixed candidate range, no I/O in the loop — was compiled from identical source and executed on the same physical host (H1) as (a) a Linux process and (b) a BareMetal unikernel under Firecracker. Comparing across different machines would measure the machines. Each configuration ran 3 trials; the guest's self-reported elapsed time was cross-checked against externally measured wall time and agreed to within 2 s.

The BareMetal build's CFLAGS in build-app.sh contain no -O flag, so application code compiles at -O0. Comparing it to an -O2 Linux build measures the compiler, not the runtime, so the matched--O0 row is the meaningful comparison.

ConfigurationCandidates/sTrialsSpread
Linux process, -O23,265,3063identical
Linux process, -O02,666,6663identical
BareMetal unikernel (default build = -O0), H1≈800,0006800,000–816,326
BareMetal unikernel, H2 (cloud)148,6982identical

Result. At matched optimisation on one host, the unikernel ran the workload 3.3× slower than the Linux process (0.80 M/s vs 2.67 M/s). Against the more commonly quoted -O2 Linux build the ratio is 4.1×, but roughly a fifth of that gap is the missing -O flag rather than the runtime.

We did not isolate the cause of the remaining 3.3×. Plausible contributors, in the order we would test them: -mcmodel=large in the port's CFLAGS (forcing 64-bit absolute addressing throughout), the provenance of the 128-bit division helper under -nodefaultlibs, and timer-interrupt overhead. The H2 figure is 5.4× below H1 and should not be read as a property of BareMetal: the two hosts differ in CPU and possibly in contention, and we could not instrument H2's hardware.

4 · Nondeterministic arithmetic

This is the most consequential result and we present it in the order we established it, because each step removed a competing explanation.

4.1 · The observation

The fixed-range benchmark returns a prime count that is a pure function of its inputs. Linux returns the same count every time. The unikernel did not.

4.2 · Ruling out the harness

Method. Run the identical range three times inside a single boot, in one process. This removes the VM lifecycle, the serial capture, the cloud API and our shell harness from the question: the three answers come from the same program in the same boot.

WORK = 40,000,000 candidates; ground truth primes = 4,268,930

Linux -O2      4,268,930   4,268,930   4,268,930   identical
Linux -O0      4,268,930   4,268,930   4,268,930   identical
BareMetal 16M  4,268,909   4,268,906   4,268,905   three different answers
BareMetal 256M 4,268,905   4,268,909   4,268,908   three different answers

Three passes per boot. The 256 MiB row rules out memory pressure; the Linux -O0 row rules out the optimisation level.

4.3 · Ruling out our test rig

H1 runs Firecracker inside a nested VM, which is an obvious suspect. We therefore deployed the same image to BareMetal Cloud (H2), on real hardware with no nesting:

BENCH_DONE pass=1 candidates=40000000 primes=4267943  (987 missing)
BENCH_DONE pass=2 candidates=40000000 primes=4268013  (917 missing)

The effect reproduces on real hardware, and is roughly two orders of magnitude larger there (≈2×10−4 vs 1.6×10−6).

4.4 · Minimal reproducer

Method. Evaluate one fixed modular exponentiation 20,000,000 times and count answers differing from the first. No primality logic, no allocation, no libc call inside the loop — only 64-bit multiply, modulo and shift through __uint128_t. A correct runtime must report zero.

static uint64_t mulmod(uint64_t a, uint64_t b, uint64_t m) {
    return (uint64_t)((__uint128_t)a * b % m);
}
/* powmod(A_BASE, A_EXP, A_MOD) evaluated 20,000,000 times */

Linux -O2             mismatches = 0
Linux -O0             mismatches = 0
BareMetal unikernel   mismatches = 32   rate 1.600e-06

4.5 · Characterisation

Errors are always undercounts in the prime benchmark — never once an overcount across all runs. This is consistent with sporadic corruption of an intermediate value inside Miller–Rabin: a damaged witness result makes a prime look composite. The reverse would require a composite to pass all twelve witnesses, which is effectively impossible. The corrupted value observed in the reproducer is not a near-miss of the correct answer but an unrelated 64-bit quantity.

Cause not established. Our evidence localises the fault to 64-bit integer arithmetic executed under BareMetal, and excludes: our primality logic, the optimisation level, memory pressure, our harness, and nested virtualisation. It does not distinguish among the remaining candidates — register or FPU/SSE state not preserved across an interrupt in the guest, a fault in the toolchain's 128-bit division helper under -nodefaultlibs, or something in the freestanding CFLAGS. The interrupt hypothesis is the one we would test first, because it predicts what we see: a low, rate-dependent error frequency, differing between hosts with different interrupt loads, in a long-running compute loop.

Impact · on workloads that count

A search workload on BareMetal will silently miss results at this error rate. It will not fabricate them — anything it reports is almost certainly genuine — but its coverage of a range cannot be claimed as exhaustive. Any BareMetal workload whose correctness depends on integer arithmetic over long runs (cryptography, checksums, financial arithmetic, consensus) should be considered affected until the cause is identified.

7 · Swarm and autonomous supervision

Three workers run as separate 16 MiB instances, hunting Cunningham chains of the first kind — p, 2p+1, 4p+3, … with every term prime. Coordination uses no coordinator, no queue and no shared storage: candidates are p = 6k − 1, and worker i of N takes those where k ≡ i (mod N). Coverage is complete and disjoint by construction, and a worker's death costs exactly its own share. Worker identity is compiled in, since BareMetal has no environment.

Chain length is steeply graded — below 8.7×107 a single worker finds 3659 chains of length 4, 140 of length 6, 18 of length 7 and exactly one of length 9 — which is what makes the workload worth distributing: more workers buy rarer results rather than more of the same.

7.2 · Two defects of our own

Both are ours rather than the platform's, and both are recorded because each was invisible from the outside.

Silent · Two thirds of the swarm did no useful work for hours

Run 01 partitioned the odd numbers by index modulo the swarm size. For any starting value this pins each worker to a fixed residue modulo 6, and two of the three classes cannot yield a chain: a worker holding p ≡ 1 (mod 6) always has 2p+1 divisible by 3, so it can never reach length 2, and a worker holding p ≡ 3 (mod 6) never sees a prime at all. All 56 results came from the single worker that drew p ≡ 5 (mod 6). Effective parallelism was 1, not 3.

The failure was invisible to every health signal: all three instances were RUNNING, networked, error-free, and posting heartbeats throughout. The only visible symptom was that the useless worker ran 22× "faster" — because each of its candidates died at the first trial division. Run 02 enumerates p = 6k − 1 and partitions on k, putting every worker in the productive class; the three then tracked within 0.96% of one another and all reported the same best chain length, against a 2100% spread before.

Measurement · A quantised counter cannot measure a rate

We first estimated ≈400,000 candidates/s per worker by sampling the reported search position twice, about two minutes apart. That field only advances once per heartbeat — every 50 million candidates — so the sample spanned a single boundary and overstated the rate by roughly 5×. A projection built on it ("1011 in about 3.4 hours") was wrong by the same factor; the correct figure is ≈17 hours. Rates must be measured over windows long compared with the counter's update interval, and the published figure above is.

7.3 · Autonomous supervision

A supervisory agent (an LLM tool-calling loop, run off-platform) inspects instance status and serial logs, and may restart a worker. It was validated by fault injection in both directions — the only honest test of a self-healing system is that it also declines to act when nothing is wrong:

ScenarioRequired behaviourObserved
All workers healthyreport all-clear, 0 corrective actions3/3 inspected, 0 actions
One worker stopped externallydetect, restart, re-verify, reportdetected, restarted, confirmed RUNNING, reported, 1 action

An earlier revision, whose safety rules lived in the model's prompt rather than in code, restarted a healthy worker because it had not recently announced a find — and the reboot left the instance stopped, degrading the system it was meant to protect. Moving the health criterion into C (status + network + absence of error lines, with find counts excluded by construction) and making the restart tool refuse a healthy target eliminated the behaviour. A relevant platform detail: instances reboot leaves an instance in STOPPED, so a caller wanting "restart" must re-check and issue start.

8 · Findings for the platform

Severity: high · Nondeterministic 64-bit arithmetic

Reproduced on two independent hosts with a 40-line program containing no libc call in its loop (§4). Zero mismatches on Linux at both optimisation levels. We would begin by auditing interrupt entry/exit register preservation in the guest, and by checking which implementation provides __udivti3/__umodti3 under -nodefaultlibs. The reproducer is in the repository below.

Severity: medium · build-app.sh compiles application code at -O0

The CFLAGS in build-app.sh carry no -O flag. On our workload this costs ≈20% against -O2 (measured on Linux with the same source). Adding a documented, overridable default would make published performance numbers fairer to the platform.

Severity: medium · mkbr0.sh can disconnect a single-NIC host

On a wired host the script enslaves the NIC to a bridge and moves the host IP onto it. On a cloud machine whose only interface is eth0, that severs the session running the script. A one-interface check, or defaulting to the NAT path when the host has a single NIC, would prevent it.

Severity: low · No PVH ELF note in baremetal.elf

QEMU's microvm machine refuses the image (Error loading uncompressed kernel without PVH ELF Note) although the virtio-mmio layout otherwise matches Firecracker's. Firecracker's loader does not require the note. Emitting it would let images be tested under QEMU where Firecracker is unavailable — as it was for us, on a host kernel with no TUN driver.

Worth documenting · 16 MiB is enough for TLS

We could find no statement of what fits in the 16 MiB instance cap, and budgeted 256 MiB defensively. mbedTLS, lwIP, curl, a full CA bundle and an active workload fit in 16 MiB with margin (§2). This is a selling point and is currently undocumented.

9 · Limitations

Single workload. All measurements use integer-heavy code with negligible memory traffic. Nothing here predicts I/O-bound or allocation-heavy behaviour.

Two hosts, unequal instrumentation. H2 is a shared platform whose CPU model, contention and scheduling we could not observe. Cross-host figures are reported separately and never averaged.

Coarse clock. Elapsed time comes from time(NULL) at 1 s resolution; runs were sized to ~50 s to hold that below ≈2%, and cross-checked against external wall time.

Small n. Three trials per configuration. The throughput figures were identical across trials, so we report the value rather than a confidence interval; this is repeatability, not a population estimate.

Search results are a lower bound. The 56 chains in §7 are confirmed finds, not a census: given §4, the swarm misses an unknown fraction of the chains in any range it covers. Every reported find was verified; no claim is made that the range was exhaustively searched.

Cause not isolated for either §3's 3.3× or §4's nondeterminism. Both are reported as observations with excluded alternatives, not as diagnoses.
