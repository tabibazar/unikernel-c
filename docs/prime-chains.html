Prime Chains on BareMetal

A machine that computes incorrectly once in every 1.6 million operations should not be trusted with arithmetic. This is the argument that it can be — and the record we intend to take with it.

Target Cunningham chain, length 6, first kind Substrate BareMetal + Firecracker, 16 MiB Budget $500

The question

This repository has established that BareMetal runs real compute inside 16 MiB with no operating system — Monte Carlo, MCMC, primality, TLS. It has also established, by controlled experiment, that the platform gets the answer wrong.

127 wrong in 200,000,000

An interrupt landing inside a multi-instruction sequence corrupts a live register. Zero errors with interrupts disabled; zero with an atomic divq. A register-preservation bug in the interrupt path, proven by controlled comparison rather than inferred — and unpatched.

Every project here has treated that as a liability to work around. The prime-search swarm has to caveat its own coverage because of it. The question this note answers is the inverse one:

Is there a class of workload for which that defect does not matter — and can this platform run it correctly today, unpatched?

The answer turns out to have a precise shape. Not "work that tolerates errors", which is vague and unfalsifiable, but work whose output is cheap to verify by someone else. If a result proves itself in milliseconds on trusted hardware, then a corrupted worker cannot inject a wrong answer into the world. It can only waste its own time.

Rungs R1–R3 · shelved

The first attempt, and why it stopped

Ant Colony Optimization was the initial candidate. The argument was structural: a corrupted pheromone write perturbs one selection probability, and evaporation erases it within a few iterations — the algorithm's forgetting mechanism doubling as error correction.

The engine was built and validated against published TSPLIB optima, and it worked. On identical hardware it also proved something useful: the same seed produced bit-identical tours on Linux and on BareMetal, five times out of five. The platform's known defect reaches general-purpose registers, not SSE, and that workload is floating point end to end — so the fault had no purchase on it.

Sharing lost on both metrics. All three migrating islands finished on the identical tour — they had synchronised by iteration 8,000 and then published the same number for 42,000 more rounds. Migration worked exactly as designed; there was simply nothing left to learn from each other.

That is a genuine result about diversity collapse, and it is also why the line was shelved. A tour is verifiable, but improving one is not a record anybody is keeping score of. The verification property was there; the scoreboard was not.

Why this target, specifically

A Cunningham chain of the first kind is a run of primes where each is 2p+1 of the last. The size records — largest known chain of a fixed short length — are tabulated in three mutually consistent public registries and accept submissions.

Three properties make it the right fit, and only the first is about ambition.

A find proves itself

The record form is m · p# · 2j − 1, and for that form the number either side is fully factored — so the primality test yields a deterministic Pocklington proof, not a probable-prime claim. Anyone can check it in milliseconds. This is what makes an untrustworthy machine usable: our platform's non-determinism means the search silently misses candidates, which costs efficiency but cannot manufacture a false positive. You only need to find one, and the finding carries its own proof.

The table contains its own test for a stale record

First- and second-kind chains have near-identical densities. So a mirror-kind record reached at the same size with ordinary public tools proves no hardness wall exists there. The k=6 first-kind record has stood since March 2015 — while the second-kind record at essentially the same size was taken in January 2025 using NewPGen and PFGW.

That is an unattended gap, not a hard one. The same test rejects the k=11–14 band, where both kinds are stuck and the bars were set by the Primecoin proof-of-work network — stale and genuinely hard. The tell is that the k=10 record is now larger than the k=11 record.

Nobody is grinding it

PrimeGrid runs no Cunningham subproject. But of the fourteen records at lengths 4 through 10, one person holds thirteen, and reset eight bars during 2026 alone. There is nothing to outspend — and a live incumbent who can retake a record in the time it takes to run the hunt.

The economics, and the one number they turn on

The whole substrate argument reduces to a single ratio. The unikernel is cheap per hour and slow per operation; it wins if and only if the price gap exceeds the speed gap.

At this price the handicap stops deciding feasibility. Even at the pessimistic end, $500 buys a real attempt at a record that has stood for eleven years. The comparison against ordinary Linux becomes a question of efficiency, not of possibility.

Which converts the engineering into a pass/fail criterion. One expected chain is roughly 7.3×109 primality tests, so:

A single PRP test must cost under 49 ms on the unikernel to fit the budget — under 16 ms to have a 95% chance of a find.

Measured native GMP with assembly is 8.6 ms at this size. The entire port exists to find out how much of that survives.

The engineering

The premise turned out to be wrong in a useful way. There was no libc to write: BareMetal's application port already ships a patched musl, built with exactly the flags GMP needs, alongside ports of lwIP, mbedTLS, curl, SQLite and CPython. So this became a library port following that project's own conventions — which also makes it upstreamable rather than a private fork.

The result that decides the budget is a relocation census. GMP's hand-tuned assembly has to survive being linked at 0xFFFF800000000000, an address no 32-bit field can hold.

That zero is the finding. Falling back to portable C would have cost another 2–4× on top of the platform penalty and pushed the hunt outside any sane budget.

Verified so far

  • Links clean. A 347 KB .app, zero undefined symbols, no allocated orphan sections, everything mapped where the linker script says.
  • Computes correctly. Five known-answer checks pass — including a Fermat test on a composite that must not return 1, so a stubbed implementation cannot sneak through. On a machine that miscomputes once in 1.6 million operations, a library that linked but computed wrong would be nearly impossible to attribute later.
  • Four host facts kept out of the target build: glibc's obstack, _FORTIFY_SOURCE rewriting memcpy into a symbol musl lacks, GMP's default stack temporaries against a stack of unknown size with no guard page, and a configure step that would otherwise detect the emulated build host instead of the target.
  • One trap recorded prominently, because it looks like the opposite of a bug: the assembly's absolute jumps are suppressed only because the host triplet contains linux. Building with x86_64-elf — which reads as the more correct choice for a freestanding target — breaks the link.

What is not done

The port has never been run. The development machine has no nested virtualisation, so the unikernel can be built, linked and inspected but not booted. Everything above is a static property of the artifact plus a correctness run on ordinary hardware.

The huntgated on the above

The remaining measurement is a single script on a bare-metal host. It builds the library, re-runs the correctness checks against that machine's own compiler, builds a Linux control from the same source and the same library, boots the unikernel, and prints the ratio.

That control is not a nicety. The 3.7× penalty this repository carries was measured on 64-bit modular arithmetic, and every budget figure since has applied it to big-integer work by assumption. One machine, one source, one library leaves the absence of an operating system as the only variable — which is the number this whole line of work has been circling.
